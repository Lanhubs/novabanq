# NovaBanq — Demo Funding Guide

**Audience:** The demo presenter, and the Flutter developer wiring the
"Add money" screen.

**Purpose:** Everything needed to demonstrate the funding flow live,
in front of judges, without depending on Flutterwave, a real bank, or
a real deposit.

---

## 1. What "funding" means in this demo

Funding is how a user gets money **into** their NovaBanq account.

**In production**, the flow is:

1. NovaBanq asks Flutterwave to issue a virtual account number for
   the user.
2. The user opens their bank app, enters that account number, and
   sends money.
3. The bank routes the payment through Flutterwave.
4. Flutterwave sends a webhook to NovaBanq.
5. NovaBanq credits the user's balance through the ledger.

**In the demo**, the same flow runs, except step 3 and the bank are
simulated. The Flutter app fires the webhook that Flutterwave would
have sent. Everything else — the virtual account, the ledger credit,
the balance change, the confirmation email — is real, live code.

**What to say to judges:**

> "The user gets a virtual account number here. In production they'd
> open their bank app, enter this number, and send money. The bank
> routes it through Flutterwave, Flutterwave sends us a webhook, and
> we credit the ledger. For the demo, this button fires the webhook
> directly — so you can see the whole pipeline work end to end."

**What NOT to claim:** that real money moved. Nothing in the demo
touches a real bank. The virtual account number is generated by
NovaBanq's mock provider, not by Flutterwave.

## 3. The endpoints

Three endpoints are involved. All three are documented in full in
`docs/api-contract.md`; this section gives only what the demo needs.

### `POST /api/v1/funding/virtual-account`

**Purpose:** Get (or create) the user's virtual account number.

**Authentication:** Firebase ID token in `Authorization: Bearer ...`.

**Request body:** none.

**Response (200):**

```json
{
  "success": true,
  "data": {
    "account_number": "1546629060",
    "bank_name": "NovaBanq GH",
    "account_name": "David Chashama Mensah",
    "currency": "GHS",
    "country": "GH",
    "provider_ref": "mock_cfc2fe49aed84907a6b9d1c91a256e58",
    "created_at": "2026-09-26T16:53:45.746965Z"
  },
  "error": null
}
```

**Key field:** `provider_ref`. The demo needs it for the webhook call.
It's stable per user — call this endpoint once per app session and
cache the value.

**Idempotent:** calling this twice returns the same account. Never a
second one.

### `POST /api/v1/webhooks/flutterwave`

**Purpose:** Simulate a deposit arriving at the virtual account.

**Authentication:** None for the mobile client. In production,
Flutterwave authenticates this call via a `verif-hash` header. For the
demo, that check is skipped — see the note below for exactly why.

**Request body:**

```json
{
  "event": "charge.completed",
  "data": {
    "id": "demo-1790461559309",
    "tx_ref": "mock_cfc2fe49aed84907a6b9d1c91a256e58",
    "amount": 250.00,
    "currency": "GHS",
    "status": "successful"
  }
}
```

| Field | Value for the demo |
|---|---|
| `event` | Always `"charge.completed"`. |
| `data.id` | **A unique string per tap.** Use `"demo-${DateTime.now().millisecondsSinceEpoch}"` or similar. The backend uses this as the idempotency key. |
| `data.tx_ref` | The `provider_ref` from the virtual account response. |
| `data.amount` | The amount the user typed. Sent as a JSON number. |
| `data.currency` | Must match the virtual account's currency. |
| `data.status` | Always `"successful"`. |

**Response (200):**

```json
{
  "success": true,
  "data": {
    "status": "ok",
    "credited": true
  },
  "error": null
}
```

**Key field:** `credited`. `true` means the ledger credited the user's
balance. `false` means the deposit was a duplicate, was rejected, or
was ignored.

### `GET /api/v1/accounts/me`

**Purpose:** Read the user's updated balance after a deposit.

**Authentication:** Firebase ID token.

**Response (200):**

```json
{
  "success": true,
  "data": {
    "currency": "GHS",
    "balance_minor": 4343000,
    "balance_display": "43,430.00",
    "updated_at": "2026-09-26T23:26:01.359Z"
  },
  "error": null
}
```

Display `balance_display` directly — it already has thousands
separators built in. See `docs/api-contract.md` Section 9 for the
full formatting rules.

## 4. The Flutter implementation

### Screen structure

Two screens:

1. **"Add money" screen** — shows the virtual account number, the bank
   name, and a "Simulate deposit" button.
2. **(Optional) Amount entry dialog** — lets the user pick the deposit
   amount before tapping simulate.

### Loading the virtual account

Call this when the "Add money" screen opens. Cache the response for
the session so you don't call it on every rebuild.

```dart
class AddMoneyController extends GetxController {
  final isLoading = true.obs;
  final virtualAccount = Rxn<VirtualAccount>();

  @override
  void onInit() {
    super.onInit();
    _loadVirtualAccount();
  }

  Future<void> _loadVirtualAccount() async {
    isLoading.value = true;
    try {
      final response = await ApiClient.post(
        '/funding/virtual-account',
        {},
      );
      virtualAccount.value = VirtualAccount.fromJson(response['data']);
    } finally {
      isLoading.value = false;
    }
  }
}
```

### Firing the simulate-deposit webhook

Called when the user taps "Simulate deposit". Generates a fresh event
id for each tap — this is what allows the user to deposit multiple
times in the same session, and also what the backend uses to prevent
double-crediting if the request is retried.

```dart
Future<void> simulateDeposit({
  required String providerRef,
  required String currency,
  required double amount,
}) async {
  // Unique per tap. Do NOT reuse an id — a second tap with the same
  // id would be treated as a duplicate and silently ignored.
  final eventId = 'demo-${DateTime.now().millisecondsSinceEpoch}';

  final response = await ApiClient.post('/webhooks/flutterwave', {
    'event': 'charge.completed',
    'data': {
      'id': eventId,
      'tx_ref': providerRef,
      'amount': amount,
      'currency': currency,
      'status': 'successful',
    },
  });

  final credited = response['data']['credited'] as bool;
  if (!credited) {
    // The credit did not land. Common causes: duplicate event id,
    // stale provider_ref, currency mismatch. Show a generic failure
    // and check the backend log — the reason is logged at CRITICAL.
    throw Exception('Deposit did not credit. See the backend log.');
  }
}
```

### Refreshing the balance

After a successful webhook call, refresh the balance. The
"Simulate deposit" call does not return the new balance — you need a
separate `GET /accounts/me`.

```dart
Future<void> refreshBalance() async {
  final response = await ApiClient.get('/accounts/me');
  balance.value = response['data']['balance_minor'] as int;
  balanceDisplay.value = response['data']['balance_display'] as String;
}
```

### Full button handler

```dart
Future<void> onSimulateDepositTapped() async {
  final account = virtualAccount.value;
  if (account == null) return;

  try {
    await simulateDeposit(
      providerRef: account.providerRef,
      currency: account.currency,
      amount: 250.00,
    );
    await refreshBalance();

    Get.snackbar(
      'Deposit received',
      'Your new balance is ${balanceDisplay.value}.',
    );
  } catch (e) {
    Get.snackbar(
      'Deposit failed',
      'Something went wrong. Please try again.',
    );
  }
}
```

### Error handling

| HTTP status | What happened | What to do |
|---|---|---|
| 200 with `credited: true` | Deposit landed | Refresh the balance |
| 200 with `credited: false` | Deposit rejected or was a duplicate | Show a generic failure; the backend log has the reason |
| 401 | Token expired | Call `getIdToken(true)` and retry once |
| 404 | User has no profile | Route back to onboarding |
| 422 | Request body malformed | Check the payload — this is a client bug |
| 500 | Backend error | Retry once; if it fails again, check the backend log |

## 5. Running the demo

### Setup (do this once, 10 minutes before the pitch)

```bash
# 1. Start the backend
uvicorn app.main:app --reload

# 2. In a second terminal, run the smoke test to confirm everything works
python -m scripts.test_funding
```

The smoke test output should show:

- Virtual account creation returns 200
- Fresh deposit returns `credited: true`
- Replay returns `credited: false`
- Balance is higher by the deposit amount
- Unknown ref returns `credited: false`

If any of those fail, **fix it before the demo**. Do not proceed to
the pitch.

### During the pitch

1. **Open the app.** Log in as the demo sender (`codewithkakes@gmail.com`).
2. **Navigate to "Add money".** Show the virtual account number on
   screen.
3. **Say the pitch line:** "The user gets a virtual account number
   here. In production they'd open their bank app, enter this number,
   and send money. The bank routes it through Flutterwave, Flutterwave
   sends us a webhook, and we credit the ledger. For the demo, this
   button fires the webhook directly — so you can see the whole
   pipeline work end to end."
4. **Tap "Simulate deposit."** The balance updates.
5. **Show the transaction history.** The new FUNDING/IN row appears.
6. **Tap "Simulate deposit" again** with the *same* event id — if you
   built the button to reuse the id, this demonstrates idempotency.
   The `credited` field comes back `false`, and the balance does not
   change.
7. **Check the email inbox** (if the demo includes notifications).
   The deposit-received email arrives.

### What to do if the demo fails live

**If the balance doesn't update:**
- Check the backend log. The webhook logs every rejection at `CRITICAL`.
- The most common cause is a stale `provider_ref` — usually because
  the underlying `funding_records` document was cleared or reset
  during testing (not something that happens in normal use — the
  endpoint is idempotent, so a user's `provider_ref` doesn't change
  on its own). Restart the "Add money" screen to reload the account.

**If the app can't reach the backend:**
- Check uvicorn is running.
- Check the app's base URL is `http://127.0.0.1:8000/api/v1` for local
  demo, or the Render URL if you're demoing against production.

**If emails don't arrive:**
- Check spam.
- Check the Brevo dashboard → Transactional → Logs for the send status.
- The email is not blocking the demo — the deposit and balance update
  happen regardless of whether the email is delivered.

## 6. Testing the backend directly (no app needed)

The smoke test script can be run at any time to exercise the full
flow without the mobile app:

```bash
python -m scripts.test_funding
```

**What it does:**

1. Signs in the demo sender via Firebase Auth.
2. Creates (or retrieves) the sender's virtual account.
3. Fires a fresh deposit webhook.
4. Fires the same webhook again — verifies the ledger rejects the
   replay.
5. Fetches the balance and prints it.
6. Fires a webhook with an unknown `provider_ref` — verifies the
   ledger refuses to credit.

**Expected output — full success:**

```
=== Create virtual account ===
status: 200
{'success': True, 'data': {'account_number': '...', ...}, 'error': None}

=== Webhook (fresh deposit) ===
status: 200
{'success': True, 'data': {'status': 'ok', 'credited': True}, 'error': None}

=== Webhook (replay, expect credited=False) ===
status: 200
{'success': True, 'data': {'status': 'ok', 'credited': False}, 'error': None}

=== Balance after funding ===
status: 200
{'success': True, 'data': {..., 'balance_minor': <N + 25000>, ...}, 'error': None}

=== Webhook (unknown ref, expect credited=False) ===
status: 200
{'success': True, 'data': {'status': 'ok', 'credited': False}, 'error': None}
```

The `balance_minor` in the fourth block is exactly **25000 more** than
the balance was before the script ran (GHS 250.00 × 100). If it's not,
the ledger is not crediting correctly — check the uvicorn log.

## 7. What's real and what's simulated

Be honest with yourself about this table before you stand in front of
judges.

| Component | Real or simulated |
|---|---|
| Virtual account number | **Simulated.** Generated by NovaBanq's mock provider, not Flutterwave. |
| Virtual account storage | **Real.** Firestore `funding_records` and `virtual_account_refs` collections. |
| Webhook receipt | **Real.** Actual HTTP POST to `/api/v1/webhooks/flutterwave`. |
| Webhook signature verification | **Simulated.** Skipped because the *active provider* is the mock — gated on provider type, not on a `demo_mode` flag, so it turns itself on automatically the moment the real Flutterwave provider becomes active (see Section 8, step 4). Verified unconditionally whenever the real provider is running. |
| Ledger credit | **Real.** Double-entry transaction, atomic Firestore commit, ledger entries written. |
| Balance update | **Real.** Reflected in `accounts/{uid}.balance_minor`. |
| Transaction record | **Real.** `transactions/{uuid}` document, visible in `/transactions`. |
| Funding-received email | **Real.** Sent via Brevo to the user's address. |
| Real money movement | **None.** No bank was involved. No Flutterwave API was called. |

**The honest one-liner:** "The pipeline is real; the deposit came from
a simulated bank instead of a real one."

## 8. Production checklist (post-hackathon)

For whoever wires in real Flutterwave later, in order:

1. Implement `FlutterwaveVirtualAccountProvider.create_virtual_account`
   to call `POST /v3/virtual-account-numbers`.
2. Implement `FlutterwaveVirtualAccountProvider.get_virtual_account`
   to look up an account by its Flutterwave-assigned `provider_ref`.
3. Change `get_virtual_account_provider()` in
   `app/infra/virtual_accounts/__init__.py` to return the Flutterwave
   provider instead of the mock.
4. Verify that the signature check in
   `app/features/funding/router.py` now runs — it's gated on the
   provider type, so switching providers turns it on automatically.
5. Add `flutterwave_api_key`, `flutterwave_secret_hash`, and
   `flutterwave_base_url` fields to `Settings` in `app/core/config.py`,
   plus a `require_flutterwave_config()` helper — following the exact
   pattern already used for Brevo, KYC, Cloudinary, and FxRatesAPI.
   These fields don't exist yet; add them before step 6, not after.
6. Set the resulting environment variables from the Flutterwave
   dashboard → Settings → Webhooks → Secret hash.
7. Point the Flutterwave dashboard's webhook URL at
   `https://your-domain/api/v1/webhooks/flutterwave`.
8. Confirm that the account numbers Flutterwave issues are accepted
   by Nigerian banks in your sandbox tests.
9. Update `docs/api-contract.md` if the response shape changes (it
   shouldn't — the interface is fixed by `VirtualAccountProvider`).

**Known limitation:** Flutterwave currently issues virtual account
numbers for NGN only through the Collect Payments product. Ghanaian
and Kenyan users cannot get a real virtual account through the same
flow — for those countries, keep the mock provider or integrate a
different provider. **Confirm South Africa's status before relying on
it either way** — some references in this project describe the gap as
Ghana + Kenya only, others (including an earlier draft of this table)
also listed South Africa as unavailable. That's a real product/vendor
research question, not a backend detail, so verify against
Flutterwave's current documentation rather than assuming either list
is authoritative.

## 9. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `credited: false` on a fresh deposit | Duplicate event id | Ensure `data.id` is unique per tap |
| `credited: false` on a fresh deposit (log says `unknown provider_ref`) | The provider_ref from the app doesn't match the user's current one — typically because `funding_records` was reset during testing, since the endpoint is idempotent and a ref shouldn't change on its own | Reload the "Add money" screen; if that doesn't fix it, check whether the Firestore record was manually cleared |
| `credited: false` (log says `currency mismatch`) | The webhook currency doesn't match the virtual account's | Use `virtualAccount.currency`, not a hardcoded value |
| 401 on virtual-account call | Token expired | Refresh with `getIdToken(true)` |
| 404 on virtual-account call | User has no profile | Complete onboarding first |
| 500 on webhook call | Backend error, see log | Restart backend, retry |
| Email not received | Brevo sender unverified or email in spam | Check Brevo dashboard and spam folder |
| Balance not updating after `credited: true` | App is caching the old balance | Call `GET /accounts/me` explicitly after the webhook |
